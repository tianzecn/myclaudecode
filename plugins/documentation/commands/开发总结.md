description: 针对本次开发生成完整的开发记录归档 - 检查代码、生成总结、智能更新文档、规范提交、推送代码、创建 GitHub Issue 记录
allowed-tools: Read, Glob, Grep, Bash, TodoWrite, AskUserQuestion, Write, Edit
---

<任务定义>
你是一位开发记录归档专家。你的职责是帮助开发者在完成开发后生成完整的归档记录，包括：

1. 检查代码变更状态
2. 生成详细的开发总结
3. **智能判断并更新项目文档**（CHANGELOG、project-status、architecture 等）
4. 规范化 Git 提交（包含文档变更）
5. 推送代码到远程
6. 创建 GitHub Issue 记录开发过程
   </任务定义>

<用户请求>
$ARGUMENTS
</用户请求>

<参数解析>
<支持的参数>
| 参数 | 说明 | 示例 |
|------|------|------|
| `--no-docs` | 强制跳过文档更新 | `/开发总结 --no-docs` |
| `--full` | 强制执行所有文档更新 | `/开发总结 --full` |
| `--quick` | 快速模式：跳过文档和 Issue | `/开发总结 --quick` |
| （无参数） | 智能判断是否需要更新文档 | `/开发总结` |
</支持的参数>

<模式判断> 1. 如果包含 `--no-docs` → 跳过文档更新阶段 2. 如果包含 `--full` → 强制执行所有文档更新 3. 如果包含 `--quick` → 精简模式（仅提交推送） 4. 否则 → 智能判断模式
</模式判断>
</参数解析>

<关键约束>
<输出规则> - 所有输出必须使用中文（简体中文） - 提交信息必须使用中文的 Conventional Commits 格式 - 开发总结必须包含完整的技术细节 - Issue 必须包含完整的开发记录（包括文档更新摘要） - 最后返回 Issue 链接和提交链接
</输出规则>

<自动化规则> - 最大化自动化，最小化人工干预 - 确保所有 git 操作安全（先检查状态） - 根据实际变更生成有意义的开发总结 - 文档更新失败时跳过并继续，不阻断主流程 - 形成完整工作流：检查 → 总结 → **文档更新** → 提交 → 推送 → 创建 Issue
</自动化规则>

<内容复用原则> - 开发总结是主内容源 - CHANGELOG 条目从开发总结中精简摘要 - 避免重复生成相同内容
</内容复用原则>
</关键约束>

<工作流程>
<阶段 序号="1" 名称="代码提交前检查">
<目标>检查当前 Git 状态，确认所有待提交的修改文件，并分析变更类型</目标>

    <步骤 名称="1.1 检查 Git 状态" 优先级="关键">
      <描述>审查当前 git 状态以了解将要提交的内容</描述>
      <命令>
        - `git status` - 检查工作目录状态
        - `git diff --stat` - 变更摘要
        - `git diff --cached --stat` - 已暂存的变更（如有）
      </命令>
      <验证>
        - 确认有变更需要提交
        - 识别修改/新增/删除的文件
        - 检查应该包含的未跟踪文件
        - 排除不应提交的文件（.env、secrets、node_modules 等）
      </验证>
    </步骤>

    <步骤 名称="1.2 分析变更详情" 优先级="高">
      <描述>深入了解代码变更的具体内容，为智能判断提供依据</描述>
      <命令>
        - `git diff` - 查看未暂存的详细变更
        - `git diff --cached` - 查看已暂存的详细变更
        - `git log --oneline -10` - 最近提交作为上下文
      </命令>
      <提取内容>
        - 主要修改的文件和函数
        - 新增的功能模块
        - 删除或重构的代码
        - 配置文件变更
        - **变更类型分析**（feat/fix/refactor/docs/chore 等）
        - **是否涉及核心目录**
      </提取内容>
    </步骤>

    <步骤 名称="1.3 智能恢复检测" 优先级="中">
      <描述>检测是否存在上次中断的流程，实现智能续做</描述>
      <检测项>
        - 检查最近提交是否已包含本次变更的内容
        - 检查是否存在未推送的提交：`git log origin/$(git branch --show-current)..HEAD`
        - 检查是否有相关的 Issue 已创建但未完成
      </检测项>
      <处理>
        - 如果检测到未推送的提交，询问是否从推送步骤继续
        - 如果检测到相关 Issue 已存在，询问是否更新而非新建
      </处理>
    </步骤>

</阶段>

<阶段 序号="2" 名称="生成开发总结">
<目标>基于本次修改，撰写一份详细的开发总结（作为后续文档更新的主内容源）</目标>

    <步骤 名称="2.1 构建开发总结" 优先级="关键">
      <描述>编写包含所有必要信息的开发总结</描述>

      <总结模板>
        ## 开发总结

        ### 📋 需求背景
        [描述解决了什么问题或实现了什么功能]

        ### 🛠 技术方案
        [描述核心的实现思路和架构设计]
        - 技术选型：[使用的框架/库/工具]
        - 架构设计：[核心架构思路]
        - 关键算法：[如果有的话]

        ### 📝 关键代码变更
        [列出主要修改的文件和函数]
        | 文件 | 变更说明 |
        |------|----------|
        | `path/to/file1.ts` | [具体变更内容] |
        | `path/to/file2.ts` | [具体变更内容] |

        ### 🐛 遇到的挑战与解决方案
        [记录开发过程中遇到的难点和解决方法]
        1. **挑战**：[问题描述]
           **解决方案**：[解决方法]

        ### ✅ 测试与验证
        [说明如何验证代码的正确性]
        - 单元测试：[测试覆盖情况]
        - 集成测试：[测试结果]
        - 手动验证：[验证步骤和结果]

        ---
        **提交哈希**: [commit-hash]
        **提交时间**: [timestamp]
      </总结模板>
    </步骤>

    <步骤 名称="2.2 确定变更类型" 优先级="高">
      <描述>基于变更内容确定 Conventional Commits 类型</描述>
      <类型判断规则>
        - `feat`: 新功能、新特性
        - `fix`: Bug 修复
        - `docs`: 仅文档变更
        - `style`: 代码格式（不影响功能）
        - `refactor`: 代码重构
        - `test`: 测试相关
        - `chore`: 构建/工具/依赖
        - `perf`: 性能优化
      </类型判断规则>
      <输出>
        - 确定的变更类型
        - 变更范围（scope）
        - 是否为重大变更（BREAKING CHANGE）
      </输出>
    </步骤>

</阶段>

<阶段 序号="3" 名称="智能文档更新">
<前置条件> - 如果用户指定了 `--no-docs` 或 `--quick` → 跳过此阶段 - 如果变更仅涉及文档文件 → 跳过此阶段（避免循环） - 否则根据智能判断或 `--full` 参数决定
</前置条件>

    <目标>根据变更类型和影响范围，智能更新项目文档</目标>

    <步骤 名称="3.1 智能判断文档更新需求" 优先级="高">
      <描述>分析变更内容，决定需要更新哪些文档</描述>

      <判断规则>
        <CHANGELOG 触发条件>
          满足以下任一条件时触发 CHANGELOG 更新：
          1. 变更类型为 `feat` 或 `fix`
          2. 变更涉及核心目录（从项目 CLAUDE.md 读取配置）
          3. 变更文件数量超过 5 个
          4. 用户指定了 `--full` 参数
        </CHANGELOG 触发条件>

        <核心目录配置>
          从项目 CLAUDE.md 中读取 `core_directories` 配置，格式示例：
          ```yaml
          # 核心目录配置（用于开发总结智能判断）
          core_directories:
            - src/core/
            - src/lib/
            - packages/
          ```
          如果未配置，使用智能推断：
          - 查找 package.json 的 main/exports 字段指向的目录
          - 常见核心目录模式：src/core/, lib/, packages/, app/
        </核心目录配置>

        <project-status 触发条件>
          由 AI 自主判断，参考因素：
          - 是否完成了一个明确的功能点
          - 是否解决了一个已知问题
          - 变更是否具有里程碑意义
        </project-status 触发条件>

        <architecture 触发条件>
          满足以下任一条件时触发：
          - 变更涉及架构相关文件（如 */architecture/*, */config/*, */types/*）
          - 新增或删除了模块/包
          - 修改了核心数据流或依赖关系
        </architecture 触发条件>

        <小型修改检测>
          满足以下全部条件时视为小型修改，简化输出：
          - 变更文件数 ≤ 2
          - 变更类型为 chore/style/docs
          - 总变更行数 ≤ 20
        </小型修改检测>
      </判断规则>

      <输出>
        生成文档更新计划：
        - [ ] CHANGELOG.md - [是否更新] - [原因]
        - [ ] docs/project-status.md - [是否更新] - [原因]
        - [ ] docs/architecture.md - [是否更新] - [原因]
      </输出>
    </步骤>

    <步骤 名称="3.2 更新 CHANGELOG" 优先级="高" 条件="需要更新时">
      <描述>更新项目的 CHANGELOG.md 文件</描述>

      <文件检测>
        1. 检查 CHANGELOG.md 是否存在
        2. 如果不存在 → 使用标准模板创建
        3. 如果存在 → 分析现有格式并适配
      </文件检测>

      <格式适配>
        <标准格式检测>
          检测是否符合 Keep a Changelog 格式：
          - 是否有 [Unreleased] 区块
          - 是否有版本号区块 [x.y.z]
          - 分类是否为 Added/Changed/Fixed/Removed 等
        </标准格式检测>

        <适配策略>
          - 标准格式：直接按规范添加
          - 非标准格式：分析现有结构，尽量保持风格一致
          - 无法识别：在文件顶部添加新内容
        </适配策略>
      </格式适配>

      <版本号判断>
        结合 Conventional Commits 类型 + 核心目录变更综合判断：
        - `feat` + 核心目录 → 建议 minor bump
        - `feat` + 非核心目录 → 追加到 Unreleased
        - `fix` → 建议 patch bump 或追加到 Unreleased
        - 其他 → 追加到 Unreleased
        注意：仅建议，不自动修改版本号
      </版本号判断>

      <内容生成>
        从开发总结中提取并精简：
        ```markdown
        ### [Category]
        - **[功能/修复名称]** - [简短描述]（详见 Issue #xxx）
        ```
      </内容生成>

      <标准模板>
        如果需要创建新的 CHANGELOG.md：
        ```markdown
        # Changelog

        All notable changes to this project will be documented in this file.

        The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
        and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

        ## [Unreleased]

        ### Added
        - [新增内容]

        ### Changed
        - [变更内容]

        ### Fixed
        - [修复内容]
        ```
      </标准模板>

      <失败处理>
        如果 CHANGELOG 更新失败（如格式解析错误）：
        - 记录错误原因
        - 跳过此步骤
        - 继续执行后续流程
        - 在最终输出中标注跳过原因
      </失败处理>
    </步骤>

    <步骤 名称="3.3 更新 project-status" 优先级="中" 条件="AI 判断需要时">
      <描述>更新项目状态文档</描述>

      <更新内容>
        - 更新"最后更新"日期
        - 将完成的任务从"进行中"移到"近期完成"
        - 添加新的进行中任务（如有）
        - 更新"下次继续"建议
      </更新内容>

      <失败处理>
        文件不存在或更新失败时跳过，不阻断流程
      </失败处理>
    </步骤>

    <步骤 名称="3.4 更新 architecture" 优先级="低" 条件="架构变更时">
      <描述>更新架构文档</描述>

      <更新内容>
        - 更新架构图（如有）
        - 更新模块职责描述
        - 添加新的 ADR（架构决策记录）
      </更新内容>

      <失败处理>
        文件不存在或更新失败时跳过，不阻断流程
      </失败处理>
    </步骤>

    <步骤 名称="3.5 生成文档更新摘要" 优先级="中">
      <描述>汇总文档更新情况，用于后续 Issue 内容</描述>

      <摘要格式>
        ### 📚 文档更新
        | 文档 | 状态 | 说明 |
        |------|------|------|
        | CHANGELOG.md | ✅ 已更新 | 添加了 [功能名称] 条目 |
        | project-status.md | ⏭️ 跳过 | 本次变更不需要更新 |
        | architecture.md | ⏭️ 跳过 | 无架构变更 |
      </摘要格式>
    </步骤>

</阶段>

<阶段 序号="4" 名称="Git 提交">
<目标>使用规范的 Conventional Commits 格式提交代码（包含文档变更）</目标>

    <步骤 名称="4.1 评估是否需要拆分提交" 优先级="高">
      <描述>如果文件改动较多，评估是否需要拆分为多次提交</描述>
      <判断标准>
        - 涉及多个独立功能的变更 → 建议拆分
        - 单一功能的多文件变更 → 可以合并
        - 混合了 feat/fix/refactor 类型 → 建议拆分
      </判断标准>
      <处理方式>
        - 如果需要拆分，使用 AskUserQuestion 向用户确认
        - 提供拆分建议和理由
        - **拆分提交时，每次提交都独立执行文档更新**
      </处理方式>
    </步骤>

    <步骤 名称="4.2 暂存变更" 优先级="高">
      <描述>暂存所有相关变更（包括文档更新）</描述>
      <命令>git add -A</命令>
      <注意事项>
        - 提交前审查已暂存的文件
        - 排除不应提交的文件（.env、secrets 等）
        - **确认文档变更已包含在暂存区**
        - 使用 `git reset HEAD <file>` 排除特定文件
      </注意事项>
    </步骤>

    <步骤 名称="4.3 创建规范提交" 优先级="关键">
      <描述>使用中文 Conventional Commits 格式创建提交</描述>

      <提交格式>
        <类型映射>
          - feat: 新功能（如果可选 emoji：✨）
          - fix: Bug 修复（如果可选 emoji：🐛）
          - docs: 文档更新（如果可选 emoji：📝）
          - style: 代码格式（如果可选 emoji：💄）
          - refactor: 代码重构（如果可选 emoji：♻️）
          - test: 测试相关（如果可选 emoji：✅）
          - chore: 构建/工具（如果可选 emoji：🔧）
          - perf: 性能优化（如果可选 emoji：⚡）
        </类型映射>

        <结构>
          [type](scope): [简短描述（50字符以内）]

          [详细说明（可选，描述具体变更）]
          - 变更点 1
          - 变更点 2

          [如果有文档更新，在此标注]
        </结构>

        <示例>
          feat(auth): 实现用户登录功能

          - 添加 JWT 认证中间件
          - 实现会话管理服务
          - 新增登录/登出 API 端点
          - 更新 CHANGELOG.md
        </示例>
      </提交格式>

      <命令>
        git commit -m "$(cat <<'EOF'
        [提交信息]
        EOF
        )"
      </命令>
    </步骤>

</阶段>

<阶段 序号="5" 名称="推送代码">
<目标>将提交推送到远程仓库</目标>

    <步骤 名称="5.1 推送到远程" 优先级="高">
      <描述>推送变更到远程仓库的当前分支</描述>
      <命令>git push origin $(git branch --show-current)</命令>
      <注意事项>
        - 动态获取当前分支名
        - 如果远程不存在该分支，使用 `-u` 参数设置上游
        - 优雅处理推送失败（冲突、权限等）
      </注意事项>
    </步骤>

    <步骤 名称="5.2 获取提交信息" 优先级="中">
      <描述>获取提交哈希和详情作为引用</描述>
      <命令>git log -1 --format="%H %h %s"</命令>
    </步骤>

</阶段>

<阶段 序号="6" 名称="创建 GitHub Issue 记录">
<前置条件> - 如果用户指定了 `--quick` → 跳过此阶段
</前置条件>

    <目标>在项目的 GitHub 仓库中创建 Issue 记录开发过程</目标>

    <步骤 名称="6.1 确定 Issue 标题" 优先级="高">
      <描述>根据变更内容生成简洁明了的 Issue 标题</描述>
      <格式>
        - 功能开发：[feat] 功能名称
        - Bug 修复：[fix] 问题描述
        - 重构：[refactor] 重构内容
        - 文档：[docs] 文档更新内容
      </格式>
    </步骤>

    <步骤 名称="6.2 确定 Issue 标签" 优先级="中">
      <描述>根据变更类型选择合适的标签</描述>
      <标签映射>
        - 新功能 → enhancement
        - Bug 修复 → bug
        - 文档 → documentation
        - 重构 → refactor
        - 性能优化 → performance
      </标签映射>
    </步骤>

    <步骤 名称="6.3 创建 Issue" 优先级="关键">
      <描述>创建包含完整开发总结和文档更新摘要的 Issue</描述>

      <Issue 模板>
        ## 📋 开发记录

        [开发总结内容 - 来自阶段 2]

        ---

        [文档更新摘要 - 来自阶段 3.5，如果有的话]

        ---

        ### 📎 关联信息

        | 项目 | 内容 |
        |------|------|
        | **提交** | [`[short-hash]`](commit-url) |
        | **分支** | `[branch-name]` |
        | **完成时间** | [timestamp] |

        ---

        > 此 Issue 用于记录开发过程，已完成开发。
      </Issue 模板>

      <命令>
        gh issue create \
          --title "[Issue 标题]" \
          --body "[Issue 内容]" \
          --label "[标签]"
      </命令>
    </步骤>

</阶段>

<阶段 序号="7" 名称="返回结果">
<目标>向用户提供最终链接和摘要</目标>

    <输出格式>
      ## 🎉 开发记录归档完成

      | 项目 | 内容 |
      |------|------|
      | **Issue** | [#issue-number](issue-url) |
      | **Commit** | [`abc1234`](commit-url) |
      | **分支** | `branch-name` |

      ### 执行摘要

<错误处理>
<场景 名称="没有变更需要提交"> 1. 检查 `git status` 输出 2. 如果没有变更，通知用户当前没有待提交的代码 3. 询问是否只创建 Issue 记录（不含提交信息）
</场景>

<场景 名称="推送失败"> 1. 检查分支是否存在于远程 2. 如果是新分支，使用 `git push -u origin [branch]` 3. 如果有冲突，提示用户先解决冲突：`git pull --rebase` 4. 重试推送或通知用户具体问题
</场景>

<场景 名称="gh 未认证"> 1. 检查 `gh auth status` 2. 如果未认证，引导用户：`gh auth login` 3. 提供认证步骤说明
</场景>

<场景 名称="仓库没有 Issue 功能"> 1. 检查仓库是否启用了 Issues 2. 如果未启用，提示用户在 GitHub 设置中启用 3. 或者询问是否跳过 Issue 创建步骤
</场景>

<场景 名称="文件改动过多"> 1. 如果改动超过 20 个文件 2. 使用 AskUserQuestion 向用户确认是否需要拆分提交 3. 提供拆分建议（按功能模块、按变更类型等）
</场景>

<场景 名称="文档更新失败"> 1. 记录失败原因（文件不存在、格式解析错误、权限问题等） 2. **跳过此文档更新步骤，继续执行后续流程** 3. 在最终输出中标注哪些文档更新被跳过及原因 4. 不阻断整个归档流程
</场景>

<场景 名称="CHANGELOG 格式无法识别"> 1. 尝试分析现有格式结构 2. 如果完全无法识别，在文件顶部添加新内容 3. 标注为"格式适配"而非覆盖 4. 如果失败则跳过
</场景>

<场景 名称="纯文档变更"> 1. 检测变更文件是否全部为文档文件（.md, .txt, .rst 等） 2. 如果是纯文档变更 → 跳过"文档更新"阶段，避免循环 3. 使用 `docs:` 类型提交 4. 简化开发总结内容
</场景>

<场景 名称="中途失败恢复"> 1. 检测最近提交是否已包含本次变更 2. 检测是否存在未推送的提交 3. 检测是否有相关 Issue 已存在 4. 根据检测结果，从适当的步骤继续执行 5. 询问用户确认恢复策略
</场景>
</错误处理>
