请分析并修复 GitHub Issue：$ARGUMENTS。

遵循以下步骤：

# 计划

1. 使用 `gh issue view` 获取 Issue 详情
   - 从 GitHub Issue 获取完整描述、标签、受让人和任何元数据。

2. 阅读并理解 Issue 中描述的问题
   - 仔细分析主要问题陈述和预期结果。

3. 识别相关或关联的**子 Issue** 和依赖关系
   - 查找：
     - 主 Issue 下链接的**子 Issue 或任务**（例如，Issue 正文中的检查清单，如 `- [ ] 创建数据库 Schema`、`- [ ] 实现 API`）。
     - **相关的 GitHub Issue**，链接为 "blocks"、"is blocked by" 或 "relates to"。
     - **在 Epic 或父故事下分组的 Issue**（如果使用项目管理工具）。
   - 将这些子 Issue 视为范围的一部分。如果它们存在，将它们纳入计划，以便解决方案高效且避免重复。
   - **示例：**
     - 主 Issue：*"实现用户认证"*
     - 找到的子 Issue：
       - `#201` 设置用户数据库 Schema
       - `#202` 创建登录 API
       - `#203` 集成 OAuth 提供商
     - 计划必须考虑所有三个，因为它们是解决主 Issue 的一部分。

4. 如果需要，提出澄清问题
   - 如果任何细节不清楚，为 Issue 作者或利益相关者准备一份澄清问题列表。

5. 了解 Issue 的先前工作
   - 在草稿本或内部文档中搜索与 Issue 相关的以前的想法。
   - 搜索以前的 PR，看看是否已经尝试过解决此问题。
   - 在代码库中搜索可能已经包含相关逻辑的相关文件、函数或模块。

6. 深入思考如何以小型和可管理的方式解决 Issue
   - 将主 Issue **及其子 Issue** 分解为更小的可操作任务。
   - 按逻辑顺序对任务进行排序，尊重依赖关系（例如，数据库在 API 之前，API 在 UI 之前）。
   - 起草一个清晰的计划，其中包含可以增量执行的待办事项。

7. 在草稿本中记录计划
   - 在文件名中包含 Issue 名称，以便于引用。
   - 在草稿本中添加 Issue 的直接链接。
   - 确保计划结构良好，以便另一个人或自动化系统可以在不需要额外上下文的情况下执行它。

# 创建
- 使用 Issue 名称创建新分支
  - 使用一致的命名约定（例如，`issue/<issue-number>-<short-description>`）
- 按照草稿本中记录的计划，以**小型、可管理的步骤**解决 Issue
  - 如果 Issue 有**子 Issue**，增量解决它们，在每个部分完成后提交
- 创建**清晰且描述性的提交消息**
  - 示例：`fix(auth): handle token refresh expiry (closes #123)`
- 完成每个步骤或子 Issue 后经常提交更改

---

# 测试
- 运行**所有相关测试**以验证修复
  - 单元测试、集成测试和端到端测试（如果可用）
- 确保代码通过：
  - ✅ Linting
  - ✅ 类型检查
- 对于错误修复：
  - 添加**回归测试**以防止再次发生
- 如果自动化测试不能覆盖所有内容，添加**手动测试步骤**

---

# 推送
- 将分支推送到远程仓库
- 创建一个**拉取请求（PR）**，在标题中包含 Issue 名称
  - 示例：`Fix: Auth Token Refresh [#123]`
- 在 PR 描述中：
  - 引用主 Issue（`Closes #123`）
  - 引用覆盖的任何子 Issue
  - 总结更改的内容和原因
- 确保 PR 遵循贡献指南：
  - ✅ 使用 PR 模板
  - ✅ 有适当的标签
  - ✅ 请求审查者
